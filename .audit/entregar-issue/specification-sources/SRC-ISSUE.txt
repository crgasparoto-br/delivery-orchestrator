## Problema

Uma execução Delivery V2 pode terminar pre-material com worker `completed/success` e sem PR gerenciada porque o worker concluiu `noop` a partir de uma versão anterior do contrato da issue.
Quando a issue alvo é materialmente atualizada depois disso, o bootstrap `reserved-initial-attempt` continua preso ao `scopeBinding.issueContractSha256` antigo. A reentrada atual só rearma esse caminho quando muda o SHA do control plane, portanto um novo dispatch no mesmo control plane recupera a tentativa antiga em vez de executar contra o contrato novo.

Caso observado: SolverFin #621, controller run 36569020189, worker 36569056972.

## Esperado

- detectar mudança do fingerprint canônico `repository + issueNumber + title + body` entre o bootstrap persistido e a issue corrente;
- para worker `completed/success` sem PR material, permitir rearmar a mesma tentativa quando o contrato da issue mudou, mesmo com o mesmo SHA do control plane;
- gerar nonce novo e persistir `scopeBinding` atualizado antes do novo worker;
- não consumir tentativa adicional;
- mesma issue fingerprint + mesmo control plane continua recuperando a execução anterior, sem retry cego;
- preservar fail-closed para bootstrap sem fingerprint/proveniência suficiente;
- adicionar testes discriminantes e atualizar o contrato documental.

## Critérios de aceite

- [ ] mudança apenas do contrato da issue rearma o bootstrap pre-material bem-sucedido sem PR;
- [ ] o rearm atualiza o `issueContractSha256` persistido;
- [ ] o número da tentativa é preservado;
- [ ] um novo `dispatchNonce` é usado;
- [ ] reentrada sem mudança de contrato nem control plane não cria nova tentativa;
- [ ] os testes de reentry/bootstrap existentes continuam verdes.
